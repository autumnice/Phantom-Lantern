# ADR: 前端重构主线选择（v1）

## 背景

当前仓库前端存在两套并存实现：

- 根入口单文件：`index.tsx`（当前实际运行）
- 模块化版本：`src/`（组件/hooks/services/types 已拆分，但未被入口引用）

前端重构需要明确“以哪套代码为主线”，否则 AI coding 容易在两套代码之间分叉、返工。

## 决策

采用 **方案 A：以 `src/` 为重构主线，最后再切换入口**。

具体规则：

- 重构期间 **冻结 `index.tsx` 为“现网可运行基线”**（只做必要安全修复/紧急修复，不做结构性重构）
- 所有新的前端重构、UI/性能改造、API client 改造都发生在 `src/` 体系内
- 等 `src/` 在 mock-server 下完成关键流程验收后，再执行一次“入口切换”任务，把运行入口从 `index.tsx` 切到 `src/App.tsx`（或新的主入口）

## 选择理由（通用原则）

- **最小化中断风险**：保留一个稳定可运行版本，避免重构期频繁 break 影响验证与迭代。
- **更适合并行开发**：前端可在 mock 下完整验收，不需要后端；入口切换作为最后一步降低耦合。
- **更适合 AI 执行**：把“改动面”收敛到 `src/`，减少 AI 在两套实现间来回修改导致的歧义。

## 代价与应对

- 代价：重构期两套代码并存，仓库维护成本增加。
- 应对：
  - 给 `index.tsx` 定“冻结规则”，避免双线演进
  - 把“入口切换”设为里程碑任务，完成后删除/归档旧入口

## 影响范围

- 前端任务（FE-0/FE-1/FE-2…）：默认以 `src/` 为改动目标
- 集成阶段：入口切换完成后再做 mock ↔ real 回切与最小集成测试

## 验收标准（DoD）

- `src/` 版本在 mock-server 下可跑通关键路径：输入 → plan → image/batch → export
- 入口切换后，应用仍能在相同验收用例下通过
